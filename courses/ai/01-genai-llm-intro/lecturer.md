# ლექტორისთვის · ლექცია 1

ეს გვერდი ლექტორისთვისაა — სტუდენტები მას ვერ ხედავენ. აქ არის თემები, რაზეც ლაპარაკობ, როგორ ახსნა, რა მაგალითები გამოიყენო, რა ჰკითხო კლასს და რა კითხვებისთვის იყო მზად. პრეზენტაციას არ კითხულობ — ის შენს ნათქვამს **აჩვენებს**.

## 🎯 ლექციის აზრი

ეს **თეორიული** ლექციაა — კოდს არ ვწერთ. ორი მიზანი:

1. **მოდულის სრული სურათი.** სტუდენტი უნდა გავიდეს იმის ცოდნით, რას ააწყობს 24 ლექციაში, რისი კეთება შეეძლება ბოლოს, რატომ ვერ აკეთებს ამას ახლა და ვინ გახდება.
2. **სწორი წარმოდგენა მოდელზე.** ტოკენი, შემდეგი ტოკენი, context, პარამეტრები, ფასი — ისე, რომ როცა მე-2 ლექციიდან კოდს დაწერენ, ეს კითხვები აღარ გაუჩნდეთ.

```tip
**ტემპი:** მშვიდად. ყოველ ახალ ცნებამდე ჯერ კლასს ჰკითხე (🙋), მოუსმინე 2–3 პასუხს, მერე ახსენი და ვიზუალზე აჩვენე. სტუდენტი უნდა **ხედავდეს** იმას, რაზეც ლაპარაკობ, და არა წარმოიდგენდეს.
```

## 1 · მოდული: რას ვაწყობთ და ვინ გავხდებით

**მთავარი სათქმელი:** აქამდე AI-ს **იყენებდნენ**, ახლა **ააწყობენ**. ბოლოს მათ API-ში იქნება აგენტი, რომელიც ადამიანის ენას იგებს და **მათი C# კოდით** მოქმედებს.

**როგორ:**

1. დაიწყე კითხვით: „სად გამოგიყენებიათ AI? რა გაგიკვირდათ — ან რა ვერ გააკეთა?“ 2–3 პასუხი. ხშირად იტყვიან: „მოიგონა რაღაც“, „არ ახსოვდა“ — დაიმახსოვრე, ორივეს დღეს ავხსნით (hallucination, stateless).
2. აჩვენე საბოლოო შედეგი — ჩატი და „აგენტი შიგნიდან“. ხაზი გაუსვი: **მოდელი წყვეტს, რა გააკეთოს; აკეთებს ჩვენი კოდი** (SearchMenu, BookTable — ჩვეულებრივი C# მეთოდები). Injection-ის მაგალითზე ჰკითხე: „რატომ არ შეასრულა?“ — „ამას ლექცია 19-ზე ისწავლით“.
3. „რა გაკლიათ?“ — ჯერ მათ ჰკითხე. ისინი იცნობენ API-ს და ბაზას; აკლიათ: მოდელთან საუბარი, ჩვენი მონაცემის მიწოდება, მოქმედება, დაცვა და გაზომვა. თითოს თავისი ლექციების ბლოკი აქვს.
4. რეალური პროექტები — აქ შენი გამოცდილება ყველაზე ძვირფასია. თითო მაგალითზე თქვი, **რა ტექნიკაა** და **რომელ ლექციაზე** ისწავლიან.
5. „ვინ გახდებით“ — AI Engineer / Agent Developer / Backend + AI. ხაზი გაუსვი: მოდელს **არ ვწვრთნით**, მზა მოდელს სისტემად ვაქცევთ.
6. დაასრულე მათი იდეით: 2 წუთი მეზობელთან — ერთი AI ფუნქცია მათი პროექტისთვის. 2–3 იდეა მოისმინე.

**რეალური მაგალითები, რომლებიც კარგად მუშაობს:**

- **ბანკის ჩატბოტი**, რომელიც ტარიფებზე პასუხობს შიდა PDF-ებიდან და წყაროს უთითებს → RAG.
- **მიტანის სერვისი**: „სად არის ჩემი შეკვეთა?“ → აგენტი სტატუსს API-დან ამოწმებს → tools.
- **HR**: 500 CV → სახელი, გამოცდილება, უნარები ბაზაში → structured output.
- **IT support**: „VPN არ მუშაობს“ → ინსტრუქცია + Jira ticket → MCP, agents.

**მოსალოდნელი კითხვები:**

```check
? „AI ჩაგვანაცვლებს დეველოპერებს?“
= მოკლედ და თემაზე დაბრუნება: AI-ს სისტემაში ჩაშენება სწორედ დეველოპერის საქმეა — მონაცემი, უსაფრთხოება, ხარჯი, ტესტები. ამ მოდულის მიზანიც ესაა. დებატებში ნუ ჩაერთვები.
? „რატომ .NET და არა Python?“
= მოდელების წვრთნა Python-ზეა. ჩვენ მზა მოდელს API-ით ვიძახებთ — ეს ნებისმიერ ენაზე კეთდება, და .NET-ს ამისთვის ოფიციალური ბიბლიოთეკები აქვს (Microsoft.Extensions.AI, Agent Framework). კომპანიების backend-ების დიდი ნაწილი .NET-ზეა — AI იქ ემატება.
? „ChatGPT ხომ იგივეა, რაც LLM?“
= ChatGPT **აპლიკაციაა** LLM-ის თავზე: ისტორია, ფაილები, ძებნა. ჩვენ სწორედ ასეთ აპლიკაციას ვაწყობთ, ოღონდ ჩვენი ბიზნესისთვის.
? „ფასიანი იქნება? Gemini უნდა ვიყიდოთ?“
= სწავლისთვის Gemini-ს უფასო ლიმიტი საკმარისია; ვისაც მეტი სურს, ფასიან ტარიფზე გადადის. key-ს საშინაოში აიღებენ.
```

## 2 · რატომ AI: სად მთავრდება if/else

**მთავარი სათქმელი:** ადამიანის ენა ზუსტი არ არის — წესებით ვერ დაიწერება. LLM „ესმის“ ენას, C# ზუსტად ასრულებს. ერთს მეორე არ ცვლის — **ვაერთებთ**.

**როგორ:** სამი კლიენტის შეტყობინება ხმამაღლა წაიკითხე, მერე 2 წუთი წყვილებში: „დაწერეთ if/else და endpoint-ის გამოძახება“. ერთ-ორ წყვილს ჰკითხე — ისინი თვითონ მივლენ დასკვნამდე, რომ „მსუბუქი“ ან „ის წითელსოუსიანი“ წესით არ იწერება.

**ანალოგია:** კალკულატორი ყოველთვის ზუსტია, მაგრამ „დაახლოებით რამდენი გამოვა?“ — ვერ გაიგებს. ადამიანი გაიგებს, მაგრამ შეიძლება შეცდეს. LLM ამ მხრივ ადამიანს ჰგავს.

**LLM = HTTP API:** სტუდენტებმა API კურსიდან იციან JSON request/response. აჩვენე, რომ მოდელთან საუბარიც უბრალოდ POST-ია: `model`, `messages`, `temperature` შედის; ტექსტი, `finish_reason` და `usage` გამოდის. `usage`-ზე თქვი: „ამაში ვიხდით ფულს — ამიტომ ვსწავლობთ ტოკენებს“.

```json Gemini-ს მოთხოვნის ფორმა (OpenAI-compatible) — მხოლოდ საჩვენებლად
POST https://generativelanguage.googleapis.com/v1beta/openai/chat/completions
{
  "model": "gemini-3.8-flash",
  "messages": [ { "role": "user", "content": "Suggest a light vegetarian dish" } ],
  "temperature": 0.7,
  "max_tokens": 200
}
```

## 3 · ტოკენები

**მთავარი სათქმელი:** მოდელი ტექსტს **ტოკენებად** კითხულობს — ნაჭრებად, რომლებსაც ნომერი აქვს. ტოკენი = ფასის, ლიმიტის და სიჩქარის ერთეული. ქართული მეტი ტოკენია.

**როგორ:**

1. **ჯერ კითხვა:** „რა არის ტოკენი? მოდელი ასოებად კითხულობს თუ სიტყვებად?“ — მოისმინე. ბევრი იტყვის „სიტყვებად“.
2. ინგლისური მაგალითი (5 ტოკენი) → „ქართულად რამდენი იქნება?“ → 10. ნამდვილი რიცხვებია (GPT-4o tokenizer).
3. **როგორ ინახება** — ოთხი ფენა: ტექსტი → UTF-8 ბაიტები (ქართული ასო 3 ბაიტია!) → ლექსიკონი (ბაიტები → ID) → `int[]`. მოდელი **მხოლოდ რიცხვებს** ხედავს. კითხვაზე „საიდან იცის, რას ნიშნავს 3293?“ — ვექტორი, ლექცია 9.
4. **ლაივ ტოკენაიზერი** — აქ მოეცი კლასს მართვა: „თქვით ნებისმიერი წინადადება“ და ჩაწერე. აუცილებლად აჩვენე:
   - ქართული წინადადება **GPT-4o** vs **GPT-4 (ძველი)**: 21 vs 117 ტოკენი — „იგივე ტექსტი ხუთჯერ ძვირი იყო“;
   - გრძელი სიტყვა („ვეგეტარიანელი“) — როგორ იშლება;
   - C# კოდი და emoji;
   - ტოკენი, რომელიც ქართული ასოს მხოლოდ ნაწილს შეიცავს (`‹E1 83›`) — ეს ბაიტების ფენის დადასტურებაა.

**დამატებითი ცოდნა შენთვის:**

- tokenizer-ი BPE ალგორითმით იქმნება: იწყებს ბაიტებით და ხშირ წყვილებს ახალ ტოკენად აერთიანებს, სანამ ლექსიკონი არ შეივსება. ამიტომ ხშირი სიტყვა ერთი ტოკენია, იშვიათი — ნაჭრებად.
- Gemini-ს საკუთარი tokenizer აქვს — რიცხვები განსხვავდება, ტენდენცია იგივეა. ზუსტი რაოდენობა API-ის პასუხის `usage`-შია.
- context window და ფასი **ტოკენებში** ითვლება, ამიტომ ქართულენოვანი სისტემის ხარჯი უფრო მაღალია.

**მოსალოდნელი კითხვები:**

```check
? „ტოკენი რატომ არ არის უბრალოდ სიტყვა?“
= სიტყვების ლექსიკონი უსასრულოა (ბრუნვები, შეცდომები, ახალი სიტყვები). ნაჭრებით ნებისმიერი ტექსტი იწერება შეზღუდული ლექსიკონით (~200 000). ხშირი სიტყვა ერთ ნაჭრად რჩება, იშვიათი იშლება.
? „რატომ არის ქართული მეტი ტოკენი?“
= ორი მიზეზი: ქართული ასო UTF-8-ში 3 ბაიტია, და tokenizer-მა ქართული ტექსტი ცოტა „ნახა“, ამიტომ ქართულ კომბინაციებს ცალკე ტოკენები ნაკლებად აქვთ. ახალ tokenizer-ებში ბევრად უკეთესია (21 vs 117).
? „Gemini-ზეც ასეა?“
= Gemini-ს თავისი tokenizer აქვს, რიცხვები სხვაა, მაგრამ ქართული ინგლისურზე მაინც ძვირია. ზუსტ რაოდენობას API-ის პასუხი (`usage`) აჩვენებს — მე-2 ლექციაზე ვნახავთ.
```

## 4 · შემდეგი ტოკენი, hallucination, context

**მთავარი სათქმელი:** მოდელი ერთ საქმეს აკეთებს — ითვლის, რომელი ტოკენი მოვა შემდეგ, ირჩევს ერთს, უმატებს და იმეორებს. ამიტომ წერს **სავარაუდოს**, არა ჭეშმარიტს, და **არ ახსოვს** წინა მოთხოვნა.

**როგორ:**

1. „როგორ წერს მოდელი პასუხს?“ — მოისმინე, მერე ციკლი დიაგრამაზე.
2. **„იყავი LLM“:** ყველამ ერთი სიტყვა დაწეროს („ხვალ საღამოს მინდა მაგიდა ___“). 5–6 პასუხი დაფაზე დაითვალე — ეს განაწილებაა. მეორე რაუნდში წინ „ვეგეტარიანელი ვარ“ — პასუხები იცვლება → „მოდელი მთელ ტექსტს ხედავს“ → prompt engineering (ლექცია 2).
3. **Hallucination:** „რა ღირს ხინკალი RestaurantApi-ში?“ — ჯერ ჰკითხე, რას უპასუხებს. ბევრი იტყვის „იტყვის, რომ არ იცის“ — არა, დამაჯერებლად მოიგონებს. წესი: **ფასი, მარაგი, ჯავშანი — მოდელის მეხსიერებიდან არასდროს.**
4. **Stateless:** „ChatGPT-ს ახსოვს, მოდელს ახსოვს?“ — უმეტესობა იტყვის „კი“. ახსენი: აპლიკაცია ყოველ ჯერზე **მთელ ისტორიას თავიდან აგზავნის** — ჩვენც ასე მოგვიწევს (ლექცია 7), და ამას ვიხდით.

**ანალოგიები:** ტელეფონის კლავიატურის „შემდეგი სიტყვის“ შეთავაზება, ოღონდ მილიარდჯერ ძლიერი. Stateless — ზარების ცენტრი, სადაც ყოველ ზარზე სხვა ოპერატორი პასუხობს: თუ წინა საუბარი ბარათზე არ წერია, არაფერი იცის.

**მოსალოდნელი კითხვები:**

```check
? „თუ მხოლოდ შემდეგ სიტყვას გამოიცნობს, კოდს და მათემატიკას როგორ ხსნის?“
= სწორი შემდეგი ტოკენის გამოსაცნობად მოდელს მილიარდობით პარამეტრში ენის, ლოგიკის, კოდის სტრუქტურის ნიმუშები უყალიბდება. ზუსტი მექანიზმი დღემდე კვლევის საგანია — ასე თქვი, ნუ მოიგონებ.
? „მოდელი ინტერნეტში ეძებს?“
= თავისით — არა. მხოლოდ თუ აპლიკაცია ძებნის tool-ს მისცემს. tool-ებს ლექცია 4-ზე და 15-ზე დავწერთ.
? „context window რამდენია?“
= მოდელზეა დამოკიდებული: ათიათასობით ტოკენიდან მილიონამდე. ზუსტი რიცხვი მოდელის დოკუმენტაციაშია.
? „რატომ არ ამბობს „არ ვიცი“?“
= მისი მიზანი სავარაუდო ტექსტია. ინსტრუქციით („თუ არ იცი, თქვი“) შეიძლება გავაუმჯობესოთ (ლექცია 2), მაგრამ გარანტია მხოლოდ ჩვენი მონაცემის მიწოდებაა (tools, RAG).
```

## 5 · პარამეტრები

**მთავარი სათქმელი:** Temperature წყვეტს, რამდენად „გაბედულად“ ირჩევს; Top-P ჭრის სუსტ ვარიანტებს; Max Tokens აჩერებს. პარამეტრი **მოთხოვნას** ეკუთვნის და ამოცანის მიხედვით ირჩევა.

**როგორ:**

1. **სლაიდერი:** ჯერ ჰკითხე „Temperature 0-ზე რას აირჩევს 10-ჯერ?“ → დააყენე 0 → 🎲. მერე 2 → 🎲 — გამოჩნდება „ბანანი“. ეს ყველაზე დასამახსოვრებელი მომენტია; დააცადე კლასს რეაქცია.
2. Top-P სლაიდერით აჩვენე, როგორ ნაცრისფრდება სუსტი ვარიანტები.
3. **Max Tokens:** მოჭრილი პასუხი → „რატომ მოიჭრა? რა ეწერება finish_reason-ში?“ → `length`. დაამატე: Gemini-ს ახალი მოდელები „ფიქრობენ“ და ფიქრის ტოკენებიც ამ ლიმიტში ითვლება — ძალიან დაბალ ლიმიტზე პასუხი ცარიელიც შეიძლება იყოს.
4. **ცხრილი** — მნიშვნელობები დამალულია: ყოველ ხაზზე სხვა სტუდენტს ჰკითხე, დაფაზე ჩაწერე, მერე გახსენი და შეადარეთ. მიმართულება (0 vs 0.7 vs 1+) უნდა ემთხვეოდეს, ზუსტი რიცხვი — არა.
5. **Reasoning:** „რესტორნის რომელ ამოცანას დასჭირდება?“ — 8 სტუმარი, 2 ბავშვი, ტერასა დაკავებულია → კი; „ღიაა კვირას?“ → არა.

**დამატებითი ცოდნა შენთვის:** მოდელი თითო ტოკენს ქულას (logit) აძლევს; ალბათობა = softmax(logit / T). პატარა T → სხვაობები იზრდება (მკვეთრი), დიდი T → მცირდება (ბრტყელი). სლაიდერი ზუსტად ამ ფორმულას იყენებს. Top-K — ზოგ პროვაიდერთან: მხოლოდ K საუკეთესო ტოკენი.

**მოსალოდნელი კითხვები:**

```check
? „Temperature 0-ზე ყოველთვის ერთნაირი იქნება?“
= თითქმის. სერვერზე გამოთვლის დეტალების გამო პატარა განსხვავება შეიძლება გამოჩნდეს — „თითქმის დეტერმინისტული“.
? „რატომ არ ვაყენებთ ყოველთვის 0-ს?“
= ჩატში პასუხი მექანიკური და განმეორებადი ხდება; კრეატიულ ტექსტზე ვარიანტები გვინდა. 0 = პროგნოზირებადი, არა „უკეთესი“.
? „Max Tokens input-საც ზღუდავს?“
= არა, მხოლოდ პასუხს. input-ს context window ზღუდავს.
```

## 6 · პროვაიდერები და ფასი

**მთავარი სათქმელი:** ვიხდით ტოკენზე; output ძვირია input-ზე; მოდელებს შორის ფასი ათჯერ და მეტად განსხვავდება. ჩვენ ვიყენებთ **Gemini**-ს; ლოკალური მოდელი საჭიროა, როცა მონაცემი გარეთ არ უნდა გავიდეს.

**როგორ:**

1. „რომელი პროვაიდერი გამოგიყენებიათ? რით განსხვავდებოდა?“
2. Cloud vs ლოკალური: „რესტორნისთვის რომელს აირჩევდით? და ბანკისთვის?“ — ბანკის მაგალითზე მონაცემის კონფიდენციალურობა თვითონ ამოვა.
3. **ხარჯი:** წყვილები ჯერ ფურცელზე ითვლიან A-ს და B-ს, მერე კალკულატორში ამოწმებთ (A ≈ $4.3, B ≈ $94.5). მერე „ქართულის გამო ×1.5“ — ხარჯი იზრდება. ჰკითხე: „საუბრის მე-10 შეტყობინებაზე input რამდენი იქნება?“ → ისტორია ყოველ ჯერზე თავიდან იგზავნება.

```note
სლაიდის ფასები საილუსტრაციოა და ეს უთხარი. რეალურ ფასს საშინაოში თვითონ ეძებენ Gemini-ს pricing გვერდზე.
```

**მოსალოდნელი კითხვები:**

```check
? „რატომ Gemini და არა ChatGPT/OpenAI?“
= სწავლისთვის უფასო ლიმიტი აქვს, ქართულად კარგად წერს და Google-ს ოფიციალური .NET SDK აქვს. კოდში პროვაიდერი ერთ ადგილას იქნება — შეცვლა იაფია (ამას კოდის ლექციებზე ნახავენ).

? „ლოკალურად შეიძლება?“
= კი, ღია მოდელებით (მაგ. Ollama) — ოღონდ კარგი GPU სჭირდება და პატარა მოდელები ქართულად სუსტია. ამ კურსში ამას არ ვიყენებთ.
```
