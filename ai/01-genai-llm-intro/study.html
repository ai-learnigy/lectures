შესავალი Generative AI-სა და LLM API-ებში

ლექციის სრული მასალა თავებად, ~30 წუთი კითხვა. შენი პროგრესი ბრაუზერში ინახება. ეს გვერდი პრეზენტაციას მიჰყვება: სლაიდის შეცვლისას შესაბამისი ნაწილი მოინიშნება.

⚡ 5 წუთში

თუ მხოლოდ ეს დაგამახსოვრდა, ლექციის მთავარი იცი:

  1. ამ მოდულში შენს API-ში ჩნდება AI აგენტი: მოდელი წყვეტს, რა გააკეთოს, ხოლო აკეთებს შენი C# კოდი.
  2. მოდელი ტექსტს ტოკენებად კითხულობს და მხოლოდ რიცხვებს ხედავს. ტოკენით ითვლება ფასი, ლიმიტი და სიჩქარე; ქართული მეტ ტოკენს იკავებს.
  3. მოდელი წერს სავარაუდო შემდეგ ტოკენს და არა ჭეშმარიტს. ფასი, მარაგი და ჯავშანი ყოველთვის ბაზიდან უნდა მოდიოდეს.
  4. მოდელს წინა მოთხოვნა არ ახსოვს: ისტორიას ყოველ ჯერზე ჩვენ ვაგზავნით და ამაშიც ვიხდით.
  5. Temperature, Top-P და Max Tokens ყოველ მოთხოვნას ამოცანის მიხედვით ეყენება. ხარჯი = ტოკენები × ფასი, და output input-ზე ძვირია.

📍 ლექცია გააცდინე?

  1. წაიკითხე თავები — სულ ~30 წთ. ყოველი თავის ბოლოს არის „შეამოწმე თავი“
  2. გაიარე ტესტი — 12 კითხვა, ქულით
  3. გააკეთე კლასის დავალება სახლში
  4. საშინაო დავალება — შემდეგ ლექციაზე განვიხილავთ

მოდული: AI აგენტების შექმნა და მართვა .NET-ში

სლაიდი 1

24 ლექცია. მოდულის ბოლოს შენი API ადამიანის ენას „გაიგებს“ და მის მაგივრად იმოქმედებს: მოძებნის მენიუში, დაამატებს კალათაში, დაჯავშნის მაგიდას. პირველ ლექციაზე ვნახავთ მთელ სურათს — რას ვისწავლით, რისი აწყობა შეგეძლება და ვინ გახდები — შემდეგ კი ვიგებთ, როგორ მუშაობს ენობრივი მოდელი შიგნიდან.

აქამდე — მომხმარებელი, ამიერიდან — შემქმნელი

სლაიდი 2

თითქმის ყველას გამოუყენებია AI: ჩატში კითხვა, კოდის დაწერა, თარგმანი. ეს AI-ის მომხმარებლის როლია. ამ მოდულში როლი იცვლება: AI-ს საკუთარ სისტემაში ჩააშენებ — შენი API-დან გამოიძახებ, შენს მონაცემს მიაწვდი, შენს C# მეთოდებს გამოაძახებინებ და გააკონტროლებ, რომ შეცდომა არ დაუშვას.

მოდულის ბოლოს — ასეთი იქნება RestaurantApi

სლაიდი 3

კლიენტი ჩვეულებრივი ენით წერს: „რამე მსუბუქი, ხორცის გარეშე, ორისთვის. და ხვალ 8-ზე მაგიდა“. AI აგენტი:

  1. ეძებს მენიუში — ჩვენი ბაზიდან (PostgreSQL), და არა „მეხსიერებიდან“; ამიტომ ფასი რეალურია.
  2. ჯავშნის მაგიდას — ჩვენი C# მეთოდით (BookTable), რომელსაც თვითონ იძახებს.
  3. სთავაზობს კალათაში დამატებას — და მოქმედებამდე თანხმობას ეკითხება.
  4. იცავს თავს — როცა ვინმე ცდილობს მოატყუოს („დაივიწყე ინსტრუქციები…“), უარს ამბობს.
  5. იზომება — რამდენი ტოკენი დაიხარჯა, რა ღირდა, რამდენ ხანს გაგრძელდა.

მარჯვენა ნაწილი — „აგენტი შიგნიდან“ — მთავარი იდეაა: მოდელი წყვეტს, რა გააკეთოს; აკეთებს ჩვენი კოდი. ეს ყველაფერი 24 ლექციაში ნაბიჯ-ნაბიჯ შენდება.

რა გაქვს — და რა გაკლია

სლაიდი 4

უკვე იცი: ASP.NET Core Web API, EF Core და PostgreSQL, DI, DTO-ები, ვალიდაცია. RestaurantApi-ში გაქვს მენიუ, კალათა, შეკვეთა, ჯავშანი. ანუ ყველაფერი, რასაც აგენტი „ხელებად“ გამოიყენებს, უკვე არსებობს.

გაკლია ოთხი რამ — და მოდული ზუსტად ამაზეა:

რა გაკლია ლექციები
როგორ ვესაუბროთ მოდელს C#-იდან, როგორ მივიღოთ პასუხი ობიექტად, რა ღირს და როგორ ვმართოთ შეცდომები 1–8
როგორ ვუპასუხოთ ჩვენი მონაცემით (embeddings, pgvector, RAG), რომ მოდელმა არ მოიგონოს 9–12
როგორ ვაქციოთ „მოქმედად“: tool-ები, აგენტები, MCP, რამდენიმე აგენტი 4, 13–18
როგორ დავიცვათ (prompt injection, guardrails) და როგორ გავზომოთ ხარისხი (evals, observability) 19–22

ოთხივე ერთი და იგივე „აგურებიდან“ შენდება — და ამ აგურებს ამ მოდულში ისწავლი.

მოდულის რუკა — რას შეძლებ ყოველი ეტაპის შემდეგ

სლაიდი 6
  1. ლექციები 1–3 · ვესაუბრებით მოდელს. როგორ მუშაობს LLM, როგორ დავწეროთ კარგი ინსტრუქცია (prompt) და მივიღოთ პასუხი C# ობიექტად, Microsoft.Extensions.AI და IChatClient.
  2. ლექციები 4–8 · მოდელი იძახებს ჩვენს C# კოდს. Tools და function calling, middleware, streaming, საუბრის ისტორია და context, შეცდომები და ხარჯის კონტროლი.
  3. ლექციები 9–12 · პასუხობს ჩვენი მონაცემით. Embeddings, PostgreSQL + pgvector, RAG — მენიუს და დოკუმენტების მიხედვით პასუხი, წყაროს მითითებით.
  4. ლექციები 13–18 · აგენტი მოქმედებს. Microsoft Agent Framework, საკუთარი tools, MCP, workflows, რამდენიმე აგენტის ერთად მუშაობა.
  5. ლექციები 19–20 · დაცული და გაზომილი. Prompt injection, guardrails, OpenTelemetry, evals — ხარისხის გაზომვა.
  6. ლექციები 21–24 · ფინალური პროექტი. შენი Web API + აგენტი, ტესტები, დაცვა.

ახალ პროექტს არ ვიწყებთ: ლექტორი ამ ყველაფერს RestaurantApi-ს ამატებს, შენ — შენს API პროექტს.

ვინ გახდები

სლაიდი 7

მოდულის შემდეგ შენ იქნები .NET დეველოპერი, რომელიც AI სისტემებს აწყობს. ვაკანსიებში ეს როლი სხვადასხვა სახელით გვხვდება:

  • AI Engineer — LLM-ს არსებულ სისტემაში აერთებს და პასუხს აგებს მონაცემზე, უსაფრთხოებაზე, ხარჯზე, ხარისხზე.
  • Agent Developer — აწყობს აგენტებს, რომლებიც სისტემაში მოქმედებენ: tool-ები, MCP, workflows.
  • Backend developer AI-ით — ჩვეულებრივი backend როლი, სადაც ფუნქციების ნაწილი AI-ზეა. ყველაზე გავრცელებული შემთხვევა.

მნიშვნელოვანი: ჩვენ მოდელს არ ვწვრთნით (ეს ML ინჟინრის/მკვლევრის საქმეა). ვიღებთ მზა მოდელს და სისტემად ვაქცევთ — ეს AI ინჟინრის სამუშაოს უდიდესი ნაწილია.

რას დაამატებდი შენს API-ს?

სლაიდი 8

ყოველ API პროექტს აქვს ადგილი, სადაც ადამიანი „ჩვეულებრივი ენით“ ითხოვს რამეს. მაგალითები:

  • 📚 ბიბლიოთეკა — „რამე მისტიკური, მოკლე, ქართველი ავტორის“ → წიგნების რეკომენდაცია ბაზიდან.
  • 🏋️ სპორტდარბაზი — „ხვალ დილით თავისუფალი ტრენერი?“ → განრიგის ძებნა და ჩაწერა.
  • 🏨 სასტუმრო — „3 ღამე, ზღვის ხედით, 300 ლარამდე“ → ოთახის ძებნა და დაჯავშნა.
  • 🛠️ სერვისის ცენტრი — „ლეპტოპი ხურდება“ → კატეგორია, ფასის შეფასება, ჩაწერა.

მოიფიქრე ერთი ასეთი ფუნქცია შენი პროექტისთვის. მოდულის მანძილზე სწორედ მას ააწყობ.

პრობლემა: კლიენტები ჩვეულებრივი ენით წერენ

სლაიდი 12

სამი რეალისტური შეტყობინება რესტორნის ჩატიდან:

  • ნინო: „რამე მსუბუქი, ხორცის გარეშე, ორისთვის, 40 ლარამდე“

სლაიდი 14

ეს ტერმინები ხშირად სინონიმებად გამოიყენება, სინამდვილეში კი ერთმანეთში ჩადგმული წრეებია: ყოველი შემდეგი წინას ნაწილია.

ტერმინი რა არის მაგალითი
AI — ხელოვნური ინტელექტი ყველაზე ფართო ცნება: ნებისმიერი პროგრამა, რომელიც „ჭკვიანურ“ ამოცანას ასრულებს. შეიძლება ჩვეულებრივი წესებით (if/else) იყოს დაწერილი ჭადრაკის პროგრამა, ნავიგატორის მარშრუტი
Machine Learning — მანქანური სწავლება წესებს პროგრამისტი არ წერს: პროგრამა თვითონ პოულობს მათ მაგალითებიდან spam ფილტრი, რომელმაც ათასობით მონიშნული წერილი „ნახა“
Deep Learning — ღრმა სწავლება ML, რომელიც მრავალშრიან ნეირონულ ქსელს იყენებს. ასე სწავლობს რთულ რამეებს: სურათს, ხმას, ენას სახით განბლოკვა, ხმის ამოცნობა
GenAI — გენერაციული AI მოდელები, რომლებიც არა მხოლოდ ცნობენ, არამედ ახალს ქმნიან სურათი აღწერით, მუსიკა, ტექსტი, კოდი
LLM — დიდი ენობრივი მოდელი GenAI ტექსტისთვის: ტექსტი შედის → ტექსტი გამოდის. „დიდი“ — მილიარდობით პარამეტრი და გიგანტური სასწავლო ტექსტი ChatGPT, Gemini, Claude

ChatGPT სამივეა — AI, Machine Learning და LLM ერთდროულად, რადგან LLM ყველა სხვა წრის შიგნითაა. მაგრამ ყველა AI არ არის LLM: ჭადრაკის ძველი პროგრამა AI-ია, ML კი არა.

ამ კურსში ჩვენ LLM-ის მომხმარებლები ვართ, არა შემქმნელები: მოდელს არ ვწვრთნით, მზა მოდელს API-ით ვიძახებთ და ჩვენს სისტემაში ვაერთებთ. ასე მუშაობს AI ინჟინრის პროფესიის უდიდესი ნაწილი.

ჩვენთვის LLM = კიდევ ერთი HTTP API

სლაიდი 15

Backend დეველოპერისთვის LLM ჯადოსნური არაფერია: ის გარე სერვისია, რომელსაც HTTP მოთხოვნას ვუგზავნით — ისევე, როგორც ამინდის ან გადახდის API-ს. თითქმის ყველა პროვაიდერი ერთნაირ ფორმატს იყენებს (ე.წ. OpenAI-compatible API). ზემოთ — Gemini-ს OpenAI-compatible მისამართი; OpenAI-ზე, Groq-ზე ან ლოკალურ Ollama-ზე მოთხოვნა თითქმის იდენტურია.

Request:

  • model — რომელ მოდელს ვეკითხებით
  • messages — შეტყობინებების სია, თითოს თავისი role აქვს (user, assistant, system — მე-2 ლექციაზე დეტალურად)
  • temperature, max_tokens — პარამეტრები, მე-3 ნაწილში

Response:

  • choices[0].message.content — პასუხის ტექსტი
  • finish_reason — რატომ შეწყვიტა წერა (stop — თვითონ დაასრულა, length — ლიმიტს მიაღწია)
  • usage — რამდენი ტოკენი დაიხარჯა. სწორედ ამაში ვიხდით ფულს.

ამ JSON-ს ხელით არ დავწერთ — C#-ში ამას .NET-ის ბიბლიოთეკა გააკეთებს — კოდს შემდეგ ლექციებზე ვწერთ. მაგრამ კარგია იცოდე, რა მიდის „კაპოტის ქვეშ“.

მთელი სურათი: რა ხდება „Send“-ის შემდეგ?

სლაიდი 17

სანამ დეტალებში შევალთ, აი, როგორ მუშაობს ენობრივი მოდელი მარტივად.

ერთხელ, წინასწარ — ვარჯიში. მოდელმა ტრილიონობით სიტყვა „წაიკითხა“ (წიგნები, ვებგვერდები, კოდი) და ისწავლა, რომელი სიტყვა რას მოსდევს. ამას კომპანიები აკეთებენ (Google, OpenAI…). ჩვენ მზა მოდელს ვიყენებთ.

ყოველ მოთხოვნაზე — 4 ნაბიჯი:

  1. ტექსტი ნაჭრებად იჭრება — „Book a table for“ → Book · a · table · for. ამ ნაჭრებს ტოკენები ჰქვია.
  2. მოდელი ითვლის, რომელი ნაჭერი მოვა შემდეგ — ყველა შესაძლო ნაჭერს ალბათობას აძლევს: two 62%, four 21%, pizza 0.1%…
  3. ირჩევს ერთს და ტექსტს უმატებს — „Book a table for two“. რამდენად „გაბედულად“ ირჩევს, ამას Temperature წყვეტს (ნაწილი 3).
  4. იმეორებს — ახლა უკვე „Book a table for two“-ს მერე რა მოვა? და ასე ნაჭერ-ნაჭერ, სანამ პასუხს არ დაასრულებს. ამიტომ ხედავ ჩატში პასუხს ნელ-ნელა, სიტყვა-სიტყვით.

ანალოგია: ტელეფონის კლავიატურა, რომელიც შემდეგ სიტყვას გთავაზობს — ოღონდ ისეთი, რომელსაც თითქმის მთელი ინტერნეტი აქვს წაკითხული.

შემდეგ სლაიდებზე თითო ნაბიჯს ჩავშლით: რა არის ტოკენი, როგორ ირჩევა შემდეგი ტოკენი, რატომ ცდება მოდელი და რას ხედავს ის ერთ მოთხოვნაში.

რა არის ტოკენი?

სლაიდი 18

ჯერ თვითონ სცადე უპასუხო: მოდელი ტექსტს ასოებად კითხულობს, სიტყვებად თუ სხვანაირად?

პასუხი: არც ერთი და არც მეორე — ტოკენებად. ტოკენი ტექსტის ნაჭერია: ხშირი სიტყვა ერთი ტოკენია, იშვიათი რამდენიმე ნაწილად იშლება, ზოგჯერ ცალკე ასოებადაც. თითო ტოკენს თავისი ნომერი (ID) აქვს, და მოდელი სინამდვილეში ამ რიცხვებს ხედავს.

  2. ნაჭრები — tokenizer ტექსტს ტოკენებად ჭრის: Book · a · table · for · two. ტოკენში ხშირად წინა ჰარიც შედის.
  3. ლექსიკონი — tokenizer-ს აქვს ცხრილი, სადაც ყოველ ნაჭერს თავისი ნომერი (ID) აქვს. GPT-4o-ს ლექსიკონში ~200 000 ნაჭერია; table = 3293.
  4. მოდელში შედის მხოლოდ რიცხვები — [6904, 261, 3293, 395, 1920]. პასუხსაც მოდელი რიცხვებად აბრუნებს, tokenizer კი მათ ისევ ტექსტად აქცევს.

როგორ „იცის“ მოდელმა, რას ნიშნავს 3293? მოდელის შიგნით თითო ნომერს შეესაბამება ვექტორი — ასობით რიცხვი, რომელიც წვრთნისას ისე „დალაგდა“, რომ მსგავსი მნიშვნელობის ტოკენები ახლოს არიან. ამ იდეას ლექცია 9-ზე (embeddings) დავუბრუნდებით — RAG სწორედ მასზე დგას.

Next-token prediction — LLM-ის მთელი საიდუმლო

სლაიდი 22

LLM ერთ საქმეს აკეთებს: იცის, რა ტოკენი მოდის შემდეგ. უფრო ზუსტად, ტექსტის საფუძველზე თითოეული შესაძლო ტოკენისთვის ითვლის ალბათობას.

ციკლი ასეთია:

  1. შეყვანა — მოდელი იღებს ტოკენების მიმდევრობას: Book a table for
  2. ალბათობები — ითვლის, რომელი ტოკენი მოვა შემდეგ: two — 62%, four — 21%, tonight — 9%, pizza — 0.1%… (რიცხვები საილუსტრაციოა)
  3. არჩევა — ირჩევს ერთს (როგორ — ამას Temperature წყვეტს, მე-3 ნაწილი)
  4. გამეორება — არჩეულს უმატებს ტექსტს და მთელ ციკლს თავიდან უშვებს: Book a table for two → შემდეგი ტოკენი → …
  5. დასასრული — როცა მოდელი სპეციალურ „დასრულების“ ტოკენს აირჩევს, ან ლიმიტს მიაღწევს (max_tokens)

ესაა ყველაფერი. ჩატი, კოდის წერა, თარგმანი — ყველაფერი ამ ერთი ციკლით ხდება. მოდელს „ფიქრი“ და „ცოდნა“ ამ ალბათობებში აქვს „ჩაწერილი“: გიგანტურ ტექსტზე ვარჯიშისას ისწავლა, რა მოსდევს რას.

backend-ის დასკვნა: ყოველი ტოკენი მოდელის ერთი სრული გაშვებაა. ამიტომ 500-ტოკენიანი პასუხი 50-ტოკენიანზე შესამჩნევად ნელია და ძვირი. ამიტომაც ჩანს ChatGPT-ში პასუხი „ნელ-ნელა იწერება“ — ეს streaming-ია (მე-6 ლექცია).

სლაიდი 23

წინადადება: „ხვალ საღამოს მინდა მაგიდა ___“

ჯერ თვითონ დაწერე ერთი სიტყვა, მერე იგივე ჰკითხე 3–4 მეგობარს. შედეგი თითქმის ყოველთვის ასეთია: უმეტესობა წერს „დავჯავშნო“, ნაწილი „ოთხისთვის“ ან „ფანჯარასთან“, და არავინ წერს „ბანანი“.

სწორედ ესაა ალბათობების განაწილება. მოდელმა ტექსტზე ვარჯიშისას ნახა, რომ ასეთ წინადადებას ყველაზე ხშირად „დავჯავშნო“ მოსდევს, ამიტომ მისი ალბათობა მაღალია. „ბანანი“ გრამატიკულად შეიძლება, მაგრამ თითქმის არასდროს გვხვდება — ალბათობა ნულთან ახლოსაა.

მნიშვნელოვანი დეტალი: ყველა ერთსა და იმავეს არ დაწერს, თუმცა ყველა პასუხი „ნორმალური“ იქნება. მოდელიც ასეა: ერთ კითხვაზე რამდენიმე სწორი გაგრძელება არსებობს, და რომელს აირჩევს — ამას Temperature წყვეტს.

რაუნდი 2 · იგივე სიტყვები, სხვა კონტექსტი

სლაიდი 24

ახლა წინადადებას წინ ერთი წინადადება დაემატა: „ვეგეტარიანელი ვარ და ხორცს არ ვჭამ. ხვალ საღამოს მინდა მაგიდა და ___“

„მწვადის“ ალბათობა თითქმის ნულამდე დაეცა, „სალათის“ და „ფხალის“ კი გაიზარდა. მოდელი შემდეგ ტოკენს მთელი ტექსტის მიხედვით ირჩევს, არა მხოლოდ ბოლო სიტყვების.

ეს ძალიან მნიშვნელოვანი დასკვნაა ჩვენთვის: რასაც მოდელს ვაწვდით, ის ცვლის პასუხს. თუ ვეტყვით „შენ რესტორნის მიმტანი ხარ, პასუხობ მოკლედ და მხოლოდ ჩვენი მენიუდან“, ალბათობები ისე შეიცვლება, რომ პასუხიც შესაბამისი იქნება. ამას ჰქვია prompt engineering (ლექცია 2), ხოლო უფრო ფართოდ — რა შეიტანო მოდელის „ხედვის არეში“ — context engineering (ლექცია 7).

საიდან „იცის“ მოდელმა — და როდის იტყუება

სლაიდი 25

მოდელი ორ ეტაპად იქმნება:

  1. Pre-training — გიგანტურ ტექსტზე (ინტერნეტი, წიგნები, კოდი) სწავლობს შემდეგი ტოკენის გამოცნობას. შედეგი: მოდელი, რომელიც ნებისმიერ ტექსტს „დამაჯერებლად აგრძელებს“, მაგრამ ჯერ ასისტენტი არ არის — კითხვას შეიძლება კიდევ ათი კითხვით „გააგრძელოს“.
  2. Fine-tuning (და RLHF) — დამატებით ვარჯიშობს დიალოგებზე და ადამიანების შეფასებებზე: სწავლობს ინსტრუქციის შესრულებას და ასისტენტის ქცევას. ასე ხდება „ჩატის“ მოდელი.

Knowledge cutoff — ვარჯიშის მონაცემები რაღაც თარიღამდეა. ამის შემდეგ მომხდარი მოდელმა არ იცის. და რაც მთავარია: ჩვენი რესტორნის მენიუ, ფასები, თავისუფალი მაგიდები მას არასდროს უნახავს.

Hallucination (ჰალუცინაცია) — როცა მოდელმა პასუხი არ იცის, ის მაინც წერს ყველაზე „სავარაუდო“ ტექსტს. „ხინკალი 1.20 ₾“ დამაჯერებლად ჟღერს, რადგან ასეთი წინადადებები ინტერნეტში ბევრია — მაგრამ ეს ჩვენი ფასი არ არის. მოდელი არ „იტყუება“ განზრახ: მისი მიზანი სავარაუდო ტექსტია და არა ჭეშმარიტი.

გამოსავალი (კურსის მთავარი თემა): მოდელს მეხსიერებიდან კი არ ვაპასუხებინებთ, ჩვენს მონაცემს ვაწვდით — tool-ით (ლექცია 4: მოდელი ჩვენს GetMenu() მეთოდს იძახებს) ან RAG-ით (ლექცია 11: შესაბამის დოკუმენტს ვპოულობთ და prompt-ში ვსვამთ).

⚠️

წესი, რომელიც მთელ კურსზე მოქმედებს: ფასი, მარაგი, ჯავშანი, ფული — მოდელის მეხსიერებიდან არასდროს. ასეთი მონაცემი ყოველთვის ჩვენი ბაზიდან მოდის.

Context window — რას „ხედავს“ მოდელი ერთ მოთხოვნაში

სლაიდი 26

Context window არის ტოკენების მაქსიმალური რაოდენობა, რასაც მოდელი ერთ მოთხოვნაში ამუშავებს — შემავალიც და გამომავალიც ერთად. თანამედროვე მოდელებთან ეს ათიათასობით ტოკენიდან მილიონამდეა (კონკრეტული რიცხვი მოდელის დოკუმენტაციაშია).

რა შედის მასში (სლაიდის ზოლი):

  • System — ინსტრუქცია მოდელისთვის („შენ რესტორნის ასისტენტი ხარ…“)
  • საუბრის ისტორია — წინა შეკითხვები და პასუხები
  • მონაცემები — მენიუ, დოკუმენტები, tool-ების პასუხები
  • კითხვა — მომხმარებლის ბოლო შეტყობინება
  • პასუხი — რასაც მოდელი დაწერს

მოდელს მეხსიერება არ აქვს (stateless). ეს ყველაზე ხშირი გაუგებრობაა. ChatGPT-ში ჩანს, თითქოს მოდელს „ახსოვს“ საუბარი — სინამდვილეში ყოველ ახალ შეტყობინებაზე აპლიკაცია მთელ ისტორიას თავიდან უგზავნის. ჩვენც ასე უნდა მოვიქცეთ: თუ ისტორიას არ გავუგზავნით, მოდელმა არ იცის, რაზე ვლაპარაკობდით. დღეს ამას კოდშიც შევამოწმებთ, ხოლო ისტორიის შენახვას PostgreSQL-ში — ლექცია 7-ზე ვისწავლით.

backend-ის დასკვნები:

  • გრძელი ისტორია = ყოველ მოთხოვნაზე მეტი ტოკენი = მეტი ფული
  • ისტორიას ბოლოს და ბოლოს ლიმიტი დაუდგება — მისი მართვა (შეკუმშვა, შერჩევა) ჩვენი საქმეა
  • მოდელი ხედავს მხოლოდ იმას, რაც ამ მოთხოვნაში ჩავსვით

🎛️ Temperature და Top-P — ლაივ

სლაიდი 30

ეს სლაიდი ნამდვილ ფორმულას იყენებს: მოდელი თითო ტოკენს „ქულას“ (logit) აძლევს, ალბათობები კი ასე ითვლება — თითო ქულა იყოფა Temperature-ზე და შემდეგ softmax-ით ალბათობად იქცევა.

  • Temperature ↓ (0-სკენ) → განაწილება მკვეთრდება: იმარჯვებს ყველაზე სავარაუდო („დავჯავშნო“). 0-ზე — თითქმის ყოველთვის იგივე.
  • Temperature ↑ (2-სკენ) → განაწილება ბრტყელდება: სუსტი ვარიანტებიც („ბანანი“) შანსს იღებენ.
  • Top-P — ალბათობით დალაგებულ სიაში ტოვებს ყველაზე სავარაუდოებს, სანამ ჯამი P-ს არ მიაღწევს; დანარჩენს (ნაცრისფრად) ჭრის.

🎲 აირჩიე 10-ჯერ — ზუსტად ისე ირჩევს, როგორც მოდელი: შემთხვევით, ამ ალბათობებით. სცადე Temperature 0, 0.7 და 2.

როდის რა: ერთი სწორი პასუხი (თარიღის ამოღება, კლასიფიკაცია) → 0; ჩატი → ~0.7; კრეატიული ტექსტი → 1+. Top-P-სა და Temperature-ს ერთად ჩვეულებრივ არ ვცვლით.

სლაიდი 31

Max Tokens (max_tokens, max_output_tokens, C#-ში MaxOutputTokens) ზღუდავს, მაქსიმუმ რამდენი ტოკენი დაწეროს მოდელმა პასუხში. ლიმიტს რომ მიაღწევს, წერა უბრალოდ წყდება — სიტყვის ან წინადადების შუაშიც.

რატომ გვჭირდება:

  • 💸 ხარჯის ზღვარი — output ტოკენი ყველაზე ძვირია; ლიმიტი გარანტიას გვაძლევს, რომ ერთი მოთხოვნა „არ გაიზრდება“.
  • ⏱️ დროის ზღვარი — მოკლე პასუხი სწრაფად მოდის.
  • 🐛 დაცვა უცნაური ქცევისგან — ზოგჯერ მოდელი ერთსა და იმავეს იმეორებს უსასრულოდ; ლიმიტი ამას აჩერებს.

Reasoning მოდელები — ჯერ ფიქრობენ, მერე პასუხობენ

სლაიდი 33

ჩვეულებრივი მოდელი პასუხის წერას მაშინვე იწყებს. Reasoning მოდელი ჯერ წერს შიდა „ფიქრს“ — ნაბიჯ-ნაბიჯ მსჯელობას (ე.წ. reasoning ან thinking ტოკენებს) — და მხოლოდ ამის შემდეგ საბოლოო პასუხს. ეს ისევ next-token prediction-ია, უბრალოდ მოდელი გაწვრთნილია, რომ პასუხამდე „ხმამაღლა იფიქროს“.

როდის ღირს: რამდენიმე ნაბიჯიანი ამოცანა — „8 სტუმარი, 2 ბავშვი, ტერასა დაკავებულია, რომელი მაგიდები გავაერთიანოთ?“, გამოთვლები, რთული წესების ერთად გათვალისწინება, აგენტის მოქმედებების დაგეგმვა.

რა ღირს:

  • 💸 ფული — reasoning ტოკენები ფასდება (ჩვეულებრივ output ტოკენებად), თუნდაც მომხმარებელს არ აჩვენო; ზოგი პროვაიდერი მათ საერთოდ არ გიჩვენებს, მხოლოდ რაოდენობას წერს usage-ში.
  • 🐢 დრო — პასუხამდე შეიძლება რამდენიმე წამი ან მეტი გავიდეს.
  • 🎛️ პარამეტრები — ზოგი reasoning მოდელი Temperature-ს არ იღებს, სამაგიეროდ აქვს „ფიქრის რაოდენობის“ პარამეტრი (მაგ. reasoning effort).

წესი: მარტივ კითხვაზე („რა ღირს ხინკალი?“, „ღიაა კვირას?“) reasoning მოდელი ზედმეტი ხარჯია. რეალურ სისტემაში ხშირად ორ მოდელს იყენებენ: სწრაფ და იაფს — უმეტესი მოთხოვნისთვის, reasoning-ს — მხოლოდ რთულისთვის.

შედეგი შემთხვევითობას შეიცავს; ერთი შეყვანა სხვადასხვა შედეგს იძლევა

ნებისმიერი პროგრამა, რომელიც „ჭკვიანურ“ ამოცანას ასრულებს

პროგრამა წესებს თვითონ პოულობს მაგალითებიდან
Deep Learning
Machine Learning მრავალშრიანი ნეირონული ქსელით
GenAI
AI, რომელიც ახალ კონტენტს ქმნის
LLM
დიდი ენობრივი მოდელი: ტექსტი შედის, ტექსტი გამოდის
ტოკენი (token)
ტექსტის ნაჭერი, რომლითაც მოდელი კითხულობს და წერს
tokenizer
პროგრამა, რომელიც ტექსტს ტოკენებად (და ID-ებად) ყოფს და პირიქით
vocabulary (ლექსიკონი)
tokenizer-ის ცხრილი: ნაჭერი → ნომერი (ID)
next-token prediction
შემდეგი ტოკენის წინასწარმეტყველება: LLM-ის ძირითადი მექანიზმი
ალბათობების განაწილება (distribution)
ყველა შესაძლო ტოკენის სია თავისი ალბათობით; ჯამი 100%
pre-training
ძირითადი ვარჯიში დიდ ტექსტზე: შემდეგი ტოკენის გამოცნობა
fine-tuning
დამატებითი ვარჯიში კონკრეტულ ქცევაზე (მაგ. ასისტენტის დიალოგი)
knowledge cutoff
თარიღი, სადამდეც მოდელის ვარჯიშის მონაცემები აღწევს
hallucination
დამაჯერებლად ნათქვამი, მაგრამ მცდარი ან მოგონილი ინფორმაცია
context window
ტოკენების მაქსიმუმი ერთ მოთხოვნაში (შემავალი + გამომავალი)
stateless
სისტემა, რომელსაც წინა მოთხოვნები არ ახსოვს; ყოველი მოთხოვნა დამოუკიდებელია
logit
მოდელის „ქულა“ თითო ტოკენისთვის, სანამ ალბათობად იქცევა
softmax
ფორმულა, რომელიც ქულებს ალბათობებად აქცევს (ჯამი 100%)
