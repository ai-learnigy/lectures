შესავალი Generative AI-სა და LLM API-ებში

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

დღის თემა

დღის თემა: შესავალი Generative AI-სა და LLM API-ებში

სლაიდი 1

RestaurantApi მზადაა: მენიუ, კალათა, შეკვეთა, ჯავშანი. მაგრამ ყველა endpoint ზუსტ მონაცემს ელოდება, კლიენტი კი წერს „რამე მსუბუქი მინდა, ხორცის გარეშე, ორისთვის“ — ასეთ ტექსტს if/else ვერ გაიგებს. დღეს ვიგებთ, რა არის ენობრივი მოდელი, როგორ წერს პასუხს შიგნიდან, რა ღირს ის — და ვაკეთებთ პირველ გამოძახებას ჩვენივე API-დან.

ლექციის ბოლოს შეძლებ:

  • ახსნა, როგორ ქმნის LLM ტექსტს: ტოკენები, next-token prediction, context window
  • Temperature-ის, Top-P-ის და Max Tokens-ის შერჩევა ამოცანის მიხედვით
  • პროვაიდერის არჩევა და თვის ხარჯის დათვლა ტოკენებით
  • LLM-ის გამოძახება C#-იდან IChatClient-ით და ტექსტის, ტოკენებისა და FinishReason-ის წაკითხვა

შესავალი

ჩვენი პროექტი: RestaurantApi

სლაიდი 3

API კურსზე ავაწყვეთ რესტორნის API:

  • 📋 მენიუ — კერძები, კატეგორიები, ფასები
  • 🛒 კალათა — კერძის დამატება, წაშლა, რაოდენობის შეცვლა
  • 🧾 შეკვეთა — კალათიდან შეკვეთის გაფორმება
  • 📅 ჯავშანი — მაგიდა, თარიღი, სტუმრების რაოდენობა

ყველა endpoint ელოდება ზუსტ, სტრუქტურირებულ მონაცემს: dishId, quantity, date. ფრონტენდი ამას ფორმებით და ღილაკებით აგროვებს. მაგრამ ადამიანი ჩატში ასე არ წერს — ის წერს „ხვალ 8-ზე ოთხნი ვიქნებით“.

ამ მოდულში ახალ პროექტს არ ვიწყებთ: იმავე RestaurantApi-ს ვამატებთ AI-ს, ლექცია-ლექცია. თქვენ კი იმავეს აკეთებთ თქვენს პროექტში.

საბოლოო შედეგი: RestaurantApi-ში ჩაშენებული „AI მიმტანი“. კლიენტი წერს ჩვეულებრივი ენით, აგენტი კი ჩვენივე endpoint-ებით მოქმედებს.

ნაწილი 1 · რას ვერ აკეთებს if / else?

სლაიდი 6

სანამ წაიკითხავ, სცადე თავად უპასუხო: რა ტიპის ამოცანას ვერ წერ ჩვეულებრივი C# კოდით, რამდენი პირობაც არ უნდა დაწერო?

პრობლემა: კლიენტები ჩვეულებრივი ენით წერენ

სლაიდი 7

სამი რეალისტური შეტყობინება რესტორნის ჩატიდან:

  • ნინო: „რამე მსუბუქი, ხორცის გარეშე, ორისთვის, 40 ლარამდე“
  • გიორგი: „ხვალ 8-ზე ოთხნი ვიქნებით, ბავშვიც გვყავს, ფანჯარასთან თუ შეიძლება“
  • ლუკა: „ის წითელსოუსიანი რაღაც მინდა, წინა კვირას რომ ავიღე, ოღონდ ნაკლებად ცხარე“

სცადე: როგორ გადააქცევდი თითოეულს ჩვენი API-ს გამოძახებად? ნინოსთვის ფილტრი isVegetarian=true, maxPrice=40 კიდევ გამოვა, მაგრამ „მსუბუქი“ რა არის — კალორია? პორცია? გიორგისთვის „ხვალ 8-ზე“ თარიღად და დროდ უნდა ვაქციოთ, „ბავშვიც“ — დამატებითი სკამი? ლუკას შემთხვევაში წინა შეკვეთებში უნდა ვეძებოთ და „წითელსოუსიანი“ კერძის აღწერას დავუკავშიროთ.

სიტყვების ძებნით (Contains("ხორცის გარეშე")) ამას ვერ დაწერ: ერთი და იგივე აზრი ათასნაირად ითქმება, შეცდომებით, ჟარგონით, ორ ენაზე. ჩვეულებრივი კოდი ზუსტ შეყვანას ელოდება — ადამიანის ენა კი ზუსტი არ არის.

AI → ML → Deep Learning → GenAI → LLM

სლაიდი 9

ეს ტერმინები ხშირად ერთმანეთის სინონიმად გამოიყენება, სინამდვილეში კი ერთმანეთში ჩადგმული წრეებია:

  • Artificial Intelligence (AI) — ყველაზე ფართო ცნება: ნებისმიერი სისტემა, რომელიც „ჭკვიანურ“ ამოცანას ასრულებს. ჭადრაკის ძველი პროგრამაც AI იყო.
  • Machine Learning (ML) — წესებს პროგრამისტი კი არ წერს, სისტემა მაგალითებიდან სწავლობს. მაგ., spam ფილტრი, რომელმაც მილიონი წერილი „ნახა“.
  • Deep Learning — ML, რომელიც მრავალშრიან ნეირონულ ქსელებს იყენებს.
  • Generative AI (GenAI) — მოდელები, რომლებიც ახალ კონტენტს ქმნიან: ტექსტს, სურათს, ხმას, კოდს.
  • LLM (Large Language Model) — GenAI, რომელიც ტექსტზეა: ტექსტი შედის, ტექსტი გამოდის. „Large“ — მილიარდობით პარამეტრი და გიგანტური სასწავლო ტექსტი.

ამ კურსში ჩვენ LLM-ის მომხმარებლები ვართ, არა შემქმნელები: მოდელს არ ვწვრთნით, მზა მოდელს API-ით ვიძახებთ და ჩვენს სისტემაში ვაერთებთ. ასე მუშაობს AI ინჟინრის პროფესიის უდიდესი ნაწილი.

ჩვენთვის LLM = კიდევ ერთი HTTP API

სლაიდი 10

Backend დეველოპერისთვის LLM ჯადოსნური არაფერია: ის გარე სერვისია, რომელსაც HTTP მოთხოვნას ვუგზავნით — ისევე, როგორც ამინდის ან გადახდის API-ს. თითქმის ყველა პროვაიდერი ერთნაირ ფორმატს იყენებს (ე.წ. OpenAI-compatible API). ზემოთ — ლოკალური Ollama-ს მისამართი, მაგრამ OpenAI-ზე, Groq-ზე ან Gemini-ზე მოთხოვნა თითქმის იდენტურია.

Request:

  • model — რომელ მოდელს ვეკითხებით
  • messages — შეტყობინებების სია, თითოს თავისი role აქვს (user, assistant, system — მე-2 ლექციაზე დეტალურად)
  • temperature, max_tokens — პარამეტრები, მე-3 ნაწილში

Response:

  • choices[0].message.content — პასუხის ტექსტი
  • finish_reason — რატომ შეწყვიტა წერა (stop — თვითონ დაასრულა, length — ლიმიტს მიაღწია)
  • usage — რამდენი ტოკენი დაიხარჯა. სწორედ ამაში ვიხდით ფულს.

ამ JSON-ს ხელით არ დავწერთ — C#-ში ამას IChatClient გააკეთებს (მე-5 ნაწილი). მაგრამ კარგია იცოდე, რა მიდის „კაპოტის ქვეშ“.

2 · როგორ მუშაობს

ნაწილი 2 · როგორ „ფიქრობს“ LLM?

სლაიდი 11

სამი იდეა, რომელიც მთელი კურსის მანძილზე დაგვჭირდება: ტოკენი (რას „კითხულობს“ მოდელი), next-token prediction (როგორ წერს პასუხს) და context window (რამდენს „ხედავს“ ერთდროულად).

ტოკენი — მოდელის „ანბანი“

სლაიდი 12

მოდელი ტექსტს ასოებად ან სიტყვებად კი არ კითხულობს, არამედ ტოკენებად. ტოკენი ტექსტის ნაჭერია: ხშირი სიტყვა ერთი ტოკენია (table), იშვიათი სიტყვა რამდენიმე ნაწილად იშლება, ზოგჯერ კი ცალკე ასოებადაც. ხშირად ტოკენში წინა ჰარიც შედის (" table").

ტექსტს ტოკენებად tokenizer ყოფს, და თითო ტოკენს ნომერს (ID) ანიჭებს. მოდელი სინამდვილეში რიცხვების მიმდევრობას ხედავს, მაგალითად [12768, 261, 3293, 395, 1920], და პასუხსაც რიცხვებად აბრუნებს, რომელსაც tokenizer ისევ ტექსტად აქცევს.

რატომ გვაინტერესებს backend-ში? იმიტომ, რომ ყველაფერი ტოკენებით ითვლება:

  • 💸 ფასი — პროვაიდერი ტოკენზე იხდის (მე-4 ნაწილი)
  • 📏 ლიმიტი — რამდენი ტექსტი ეტევა ერთ მოთხოვნაში (context window)
  • ⏱️ სიჩქარე — პასუხი ტოკენ-ტოკენ იწერება; მეტი ტოკენი = მეტი ლოდინი
💡

ზემოთ ტოკენებად დაყოფა და ID-ები საილუსტრაციოა. სხვადასხვა მოდელს სხვადასხვა tokenizer აქვს, ამიტომ ერთი და იგივე ტექსტი სხვადასხვა რაოდენობის ტოკენად იშლება. ზუსტი რიცხვის სანახავად — შემდეგი სლაიდის თამაში.

🎮 თამაში 1 · რამდენი ტოკენია?

სლაიდი 13

ორი წინადადება, ერთი აზრი:

  • 🇬🇧 I'd like to book a table for four people tomorrow at 8 pm.
  • 🇬🇪 მინდა ხვალ საღამოს 8 საათზე ოთხი ადამიანისთვის მაგიდა დავჯავშნო.

ჯერ გამოიცანი, თითოეული რამდენ ტოკენად დაიშლება, მერე შეამოწმე tokenizer-ის საიტზე: tiktokenizer.vercel.app (აირჩიე ახალი მოდელის tokenizer, მაგ. o200k_base) ან platform.openai.com/tokenizer.

რას დაინახავ: ინგლისური სიტყვა ხშირად ერთი ტოკენია, ქართული კი რამდენიმე ნაწილად იშლება. მიზეზი მარტივია: tokenizer იმ ტექსტზე „ისწავლა“, რაც ინტერნეტში ყველაზე ბევრია, და ქართული ტექსტი იქ ცოტაა.

რას ნიშნავს ეს ჩვენთვის:

  • 💸 ქართული მოთხოვნა უფრო ძვირია — ფასი ტოკენზეა
  • ⏱️ ქართული პასუხი უფრო ნელა იწერება — მეტი ტოკენი უნდა დაიწეროს
  • 📏 context window-ში ქართული ტექსტი ნაკლები ეტევა
  • 🎯 პატარა მოდელები ქართულად ხშირად უარესად წერენ — ეს დღესვე ვნახავთ ლოკალურ მოდელზე
👉

ეს არ ნიშნავს, რომ ქართული არ გამოვიყენოთ — კლიენტი ქართულად წერს. ნიშნავს, რომ ხარჯის დათვლისას და მოდელის არჩევისას ქართული ტექსტით ვამოწმებთ და არა ინგლისურით. ზოგი გამოცდილი გუნდი შიდა ინსტრუქციებს (system prompt) ინგლისურად წერს, მომხმარებელს კი ქართულად პასუხობს.

Next-token prediction — LLM-ის მთელი საიდუმლო

სლაიდი 14

LLM ერთ საქმეს აკეთებს: იცის, რა ტოკენი მოდის შემდეგ. უფრო ზუსტად, ტექსტის საფუძველზე თითოეული შესაძლო ტოკენისთვის ითვლის ალბათობას.

ციკლი ასეთია:

  1. შეყვანა — მოდელი იღებს ტოკენების მიმდევრობას: Book a table for
  2. ალბათობები — ითვლის, რომელი ტოკენი მოვა შემდეგ: two — 62%, four — 21%, tonight — 9%, pizza — 0.1%… (რიცხვები საილუსტრაციოა)
  3. არჩევა — ირჩევს ერთს (როგორ — ამას Temperature წყვეტს, მე-3 ნაწილი)
  4. გამეორება — არჩეულს უმატებს ტექსტს და მთელ ციკლს თავიდან უშვებს: Book a table for two → შემდეგი ტოკენი → …
  5. დასასრული — როცა მოდელი სპეციალურ „დასრულების“ ტოკენს აირჩევს, ან ლიმიტს მიაღწევს (max_tokens)

ესაა ყველაფერი. ჩატი, კოდის წერა, თარგმანი — ყველაფერი ამ ერთი ციკლით ხდება. მოდელს „ფიქრი“ და „ცოდნა“ ამ ალბათობებში აქვს „ჩაწერილი“: გიგანტურ ტექსტზე ვარჯიშისას ისწავლა, რა მოსდევს რას.

backend-ის დასკვნა: ყოველი ტოკენი მოდელის ერთი სრული გაშვებაა. ამიტომ 500-ტოკენიანი პასუხი 50-ტოკენიანზე შესამჩნევად ნელია და ძვირი. ამიტომაც ჩანს ChatGPT-ში პასუხი „ნელ-ნელა იწერება“ — ეს streaming-ია (მე-6 ლექცია).

სლაიდი 15

წინადადება: „ხვალ საღამოს მინდა მაგიდა ___“

ჯერ თვითონ დაწერე ერთი სიტყვა. ლექციაზე ყველა სტუდენტი წერს თავის ვარიანტს, და შედეგი თითქმის ყოველთვის ასეთია: უმეტესობა წერს „დავჯავშნო“, ნაწილი „ოთხისთვის“ ან „ფანჯარასთან“, და არავინ წერს „ბანანი“.

სწორედ ესაა ალბათობების განაწილება. მოდელმა ტექსტზე ვარჯიშისას ნახა, რომ ასეთ წინადადებას ყველაზე ხშირად „დავჯავშნო“ მოსდევს, ამიტომ მისი ალბათობა მაღალია. „ბანანი“ გრამატიკულად შეიძლება, მაგრამ თითქმის არასდროს გვხვდება — ალბათობა ნულთან ახლოსაა.

მნიშვნელოვანი დეტალი: ჯგუფში ყველამ ერთი და იგივე არ დაწერა, თუმცა ყველა პასუხი „ნორმალური“ იყო. მოდელიც ასეა: ერთ კითხვაზე რამდენიმე სწორი გაგრძელება არსებობს, და რომელს აირჩევს — ამას Temperature წყვეტს.

რაუნდი 2 · იგივე სიტყვები, სხვა კონტექსტი

სლაიდი 16

ახლა წინადადებას წინ ერთი წინადადება დაემატა: „ვეგეტარიანელი ვარ და ხორცს არ ვჭამ. ხვალ საღამოს მინდა მაგიდა და ___“

„მწვადის“ ალბათობა თითქმის ნულამდე დაეცა, „სალათის“ და „ფხალის“ კი გაიზარდა. მოდელი შემდეგ ტოკენს მთელი ტექსტის მიხედვით ირჩევს, არა მხოლოდ ბოლო სიტყვების.

ეს ძალიან მნიშვნელოვანი დასკვნაა ჩვენთვის: რასაც მოდელს ვაწვდით, ის ცვლის პასუხს. თუ ვეტყვით „შენ რესტორნის მიმტანი ხარ, პასუხობ მოკლედ და მხოლოდ ჩვენი მენიუდან“, ალბათობები ისე შეიცვლება, რომ პასუხიც შესაბამისი იქნება. ამას ჰქვია prompt engineering (ლექცია 2), ხოლო უფრო ფართოდ — რა შეიტანო მოდელის „ხედვის არეში“ — context engineering (ლექცია 7).

საიდან „იცის“ მოდელმა — და როდის იტყუება

სლაიდი 17

მოდელი ორ ეტაპად იქმნება:

  1. Pre-training — გიგანტურ ტექსტზე (ინტერნეტი, წიგნები, კოდი) სწავლობს შემდეგი ტოკენის გამოცნობას. შედეგი: მოდელი, რომელიც ნებისმიერ ტექსტს „დამაჯერებლად აგრძელებს“, მაგრამ ჯერ ასისტენტი არ არის — კითხვას შეიძლება კიდევ ათი კითხვით „გააგრძელოს“.
  2. Fine-tuning (და RLHF) — დამატებით ვარჯიშობს დიალოგებზე და ადამიანების შეფასებებზე: სწავლობს ინსტრუქციის შესრულებას და ასისტენტის ქცევას. ასე ხდება „ჩატის“ მოდელი.

Knowledge cutoff — ვარჯიშის მონაცემები რაღაც თარიღამდეა. ამის შემდეგ მომხდარი მოდელმა არ იცის. და რაც მთავარია: ჩვენი რესტორნის მენიუ, ფასები, თავისუფალი მაგიდები მას არასდროს უნახავს.

Hallucination (ჰალუცინაცია) — როცა მოდელმა პასუხი არ იცის, ის მაინც წერს ყველაზე „სავარაუდო“ ტექსტს. „ხინკალი 1.20 ₾“ დამაჯერებლად ჟღერს, რადგან ასეთი წინადადებები ინტერნეტში ბევრია — მაგრამ ეს ჩვენი ფასი არ არის. მოდელი არ „იტყუება“ განზრახ: მისი მიზანი სავარაუდო ტექსტია და არა ჭეშმარიტი.

გამოსავალი (კურსის მთავარი თემა): მოდელს მეხსიერებიდან კი არ ვაპასუხებინებთ, ჩვენს მონაცემს ვაწვდით — tool-ით (ლექცია 4: მოდელი ჩვენს GetMenu() მეთოდს იძახებს) ან RAG-ით (ლექცია 11: შესაბამის დოკუმენტს ვპოულობთ და prompt-ში ვსვამთ).

⚠️

წესი, რომელიც მთელ კურსზე მოქმედებს: ფასი, მარაგი, ჯავშანი, ფული — მოდელის მეხსიერებიდან არასდროს. ასეთი მონაცემი ყოველთვის ჩვენი ბაზიდან მოდის.

Context window — რას „ხედავს“ მოდელი ერთ მოთხოვნაში

სლაიდი 18

Context window არის ტოკენების მაქსიმალური რაოდენობა, რასაც მოდელი ერთ მოთხოვნაში ამუშავებს — შემავალიც და გამომავალიც ერთად. თანამედროვე მოდელებთან ეს ათიათასობით ტოკენიდან მილიონამდეა (კონკრეტული რიცხვი მოდელის დოკუმენტაციაშია).

რა შედის მასში (სლაიდის ზოლი):

  • System — ინსტრუქცია მოდელისთვის („შენ რესტორნის ასისტენტი ხარ…“)
  • საუბრის ისტორია — წინა შეკითხვები და პასუხები
  • მონაცემები — მენიუ, დოკუმენტები, tool-ების პასუხები
  • კითხვა — მომხმარებლის ბოლო შეტყობინება
  • პასუხი — რასაც მოდელი დაწერს

მოდელს მეხსიერება არ აქვს (stateless). ეს ყველაზე ხშირი გაუგებრობაა. ChatGPT-ში ჩანს, თითქოს მოდელს „ახსოვს“ საუბარი — სინამდვილეში ყოველ ახალ შეტყობინებაზე აპლიკაცია მთელ ისტორიას თავიდან უგზავნის. ჩვენც ასე უნდა მოვიქცეთ: თუ ისტორიას არ გავუგზავნით, მოდელმა არ იცის, რაზე ვლაპარაკობდით. დღეს ამას კოდშიც შევამოწმებთ, ხოლო ისტორიის შენახვას PostgreSQL-ში — ლექცია 7-ზე ვისწავლით.

Temperature — რამდენად „გაბედულად“ ირჩევს მოდელი

სლაიდი 22

Temperature ცვლის ალბათობების განაწილების ფორმას, სანამ მოდელი ტოკენს აირჩევს. ჩვეულებრივ დიაპაზონია 0–2 (ზოგ პროვაიდერთან 0–1).

  • 0 — განაწილება იმდენად „მკვეთრდება“, რომ თითქმის ყოველთვის ყველაზე სავარაუდო ტოკენი იმარჯვებს. ერთ კითხვაზე პასუხი (თითქმის) ყოველთვის ერთნაირია.
  • ~0.7 — ბუნებრივი ტექსტი: ძირითადად სავარაუდო ტოკენები, მაგრამ ზოგჯერ სხვაც. ჩატისთვის ხშირი არჩევანია.
  • 1.5 — განაწილება „ბრტყელდება“: სუსტი ვარიანტებიც სერიოზულ შანსს იღებენ. ტექსტი მრავალფეროვანია, მაგრამ იზრდება სისულელის შანსი („ბანანი“).

როდის რა:

  • დაბალი (0–0.3) — როცა ერთი სწორი პასუხი არსებობს: შეკვეთის ტიპის დადგენა, JSON-ის ამოღება ტექსტიდან, კლასიფიკაცია.
  • საშუალო (0.5–0.9) — ჩვეულებრივი საუბარი, ახსნა, რეკომენდაცია.
  • მაღალი (1+) — კრეატიული ტექსტი: კერძის „მარკეტინგული“ აღწერა, სლოგანის ვარიანტები.
💡

Temperature = 0 ყოველთვის არ ნიშნავს ბაიტ-ბაიტ ერთნაირ პასუხს: სერვერზე გამოთვლის დეტალების გამო პატარა განსხვავება მაინც შეიძლება გამოჩნდეს. „თითქმის დეტერმინისტული“ — ასე ჯობია ვთქვათ.

  • 🐛 დაცვა უცნაური ქცევისგან — ზოგჯერ მოდელი ერთსა და იმავეს იმეორებს უსასრულოდ; ლიმიტი ამას აჩერებს.

ლიმიტი ძალიან დაბალი რომ იყოს, მომხმარებელი მოჭრილ წინადადებას მიიღებს. ამიტომ backend-ში finish_reason == length ყოველთვის უნდა შევამოწმოთ (დალოგოთ, ან ლიმიტი გავზარდოთ). დღეს ამას კოდშიც ვნახავთ.

Reasoning მოდელები — ჯერ ფიქრობენ, მერე პასუხობენ

სლაიდი 26

ჩვეულებრივი მოდელი პასუხის წერას მაშინვე იწყებს. Reasoning მოდელი ჯერ წერს შიდა „ფიქრს“ — ნაბიჯ-ნაბიჯ მსჯელობას (ე.წ. reasoning ან thinking ტოკენებს) — და მხოლოდ ამის შემდეგ საბოლოო პასუხს. ეს ისევ next-token prediction-ია, უბრალოდ მოდელი გაწვრთნილია, რომ პასუხამდე „ხმამაღლა იფიქროს“.

როდის ღირს: რამდენიმე ნაბიჯიანი ამოცანა — „8 სტუმარი, 2 ბავშვი, ტერასა დაკავებულია, რომელი მაგიდები გავაერთიანოთ?“, გამოთვლები, რთული წესების ერთად გათვალისწინება, აგენტის მოქმედებების დაგეგმვა.

რა ღირს:

  • 💸 ფული — reasoning ტოკენები ფასდება (ჩვეულებრივ output ტოკენებად), თუნდაც მომხმარებელს არ აჩვენო; ზოგი პროვაიდერი მათ საერთოდ არ გიჩვენებს, მხოლოდ რაოდენობას წერს usage-ში.
  • 🐢 დრო — პასუხამდე შეიძლება რამდენიმე წამი ან მეტი გავიდეს.
  • 🎛️ პარამეტრები — ზოგი reasoning მოდელი Temperature-ს არ იღებს, სამაგიეროდ აქვს „ფიქრის რაოდენობის“ პარამეტრი (მაგ. reasoning effort).

წესი: მარტივ კითხვაზე („რა ღირს ხინკალი?“, „ღიაა კვირას?“) reasoning მოდელი ზედმეტი ხარჯია. რეალურ სისტემაში ხშირად ორ მოდელს იყენებენ: სწრაფ და იაფს — უმეტესი მოთხოვნისთვის, reasoning-ს — მხოლოდ რთულისთვის.

IChatClient — LLM-ის „DbContext“

EF Core-იდან ეს იდეა უკვე იცი: კოდს DbContext-ით და LINQ-ით წერ, ბაზასთან კი provider ლაპარაკობს (SqlServer, Npgsql). ბაზის შეცვლა = provider-ის შეცვლა; LINQ ადგილზე რჩება.

  • ChatResponse — პასუხი: Text (ტექსტი), Usage (ტოკენები: InputTokenCount, OutputTokenCount), FinishReason (stop / length).

დაიმახსოვრე:

  1. ტოკენი — ტექსტის ნაჭერი; მისით ითვლება ფასი, context window-ის ლიმიტი და სიჩქარე. ქართული ტექსტი ბევრად მეტი ტოკენია.
  2. Next-token prediction — მოდელი წერს სავარაუდო ტექსტს, არა აუცილებლად ჭეშმარიტს (hallucination). ფასი, მარაგი, ჯავშანი — ყოველთვის ჩვენი ბაზიდან.
  3. Stateless — მოდელს წინა მოთხოვნა არ ახსოვს; ისტორიას ჩვენ ვუგზავნით და ჩვენ ვიხდით.
  4. Temperature, Top-P, Max Tokens — მოთხოვნის პარამეტრები; ამოცანის მიხედვით ვირჩევთ. finish_reason = length → პასუხი მოიჭრა.
  5. პროვაიდერი და ფასი — input იაფია, output ძვირი; მოდელებს შორის განსხვავება ათჯერადია. ლოკალური Ollama — უფასო ექსპერიმენტისთვის.
  6. IChatClient — ერთი interface; პროვაიდერის შეცვლა = ობიექტის შექმნის ერთი ადგილი.
